# Com-IS-Assist — Technical Concept

## 1. Overview

`Goal.md` sets out the target: a realtime GStreamer plugin and a VST3 plugin that automix an International Sound "Bed" (2–6 channels) against a Dialogue "Com" channel (mono), based on the COM/IS loudness-ratio concept from Jonas Engel's bachelor thesis (Hochschule Darmstadt). This document defines *how*.

The existing Reaper JSFX meter (`Ressouces/Com-IS Plugin/COM_IS_RATIO_Meter_5.1_V7.2.txt`) already demonstrates the concept — BS.1770 K-weighting, windowed momentary/short-term loudness, and a COM/IS ratio calculation — but it is **display-only**: there is no gain/duck/reduce/automix code anywhere in it. It measures; it never adjusts levels. It's also locked into Reaper/EEL2 and a single plugin host. The new engineering work is therefore:

1. Get standards-conformant R128/BS.1770 loudness measurement via an existing library, rather than hand-porting the JSFX's implementation.
2. Add the missing automatic gain-reduction layer (the actual "automix") — this part genuinely doesn't exist anywhere yet.
3. Expose that as both a GStreamer element and a VST3 plugin from **one shared DSP core**, so the two never diverge in behavior.

### Decisions this concept is built around

- **Prefer existing, well-tested libraries over hand-rolled ports wherever one fits.** R128/BS.1770 loudness measurement → `ebur128` (pure Rust, EBU-conformance-tested). Sample-rate conversion → `rubato` (pure Rust). Denoising → `nnnoiseless` (pure-Rust RNNoise port) / DeepFilterNet's native `libDF`. VAD → Silero via `ort`. The COM/IS ratio-hold policy and the multi-stage automix gain computer stay bespoke (nothing off-the-shelf implements this specific behavior), but their generic building blocks (envelope followers, one-pole smoothers) can still lean on a small permissively-licensed DSP crate instead of being hand-rolled from scratch.
- **Shared Rust core, thin wrappers.** Both plugin formats are wrappers around one `com-is-assist-core` crate — no independent DSP reimplementations. (This project was originally scoped in C++/CMake; it was migrated to Rust after an ecosystem evaluation found an unusually strong fit — see git history for the rationale. The DSP/product design in this document is unchanged by that migration; only the implementation substrate is.)
- **Voice cleaning/VAD is measurement-only for now.** Denoising and VAD clean an internal analysis copy of the dialogue, used purely to get an accurate COM loudness reading and to gate when loudness is integrated. The real Dialogue/Mix outputs stay pristine. This is architected as a swappable tap, not hardcoded, since cleaned audio may be promoted to the actual output later if quality allows.
- **Build order: GStreamer first, VST3 second.** GStreamer is the real broadcast/OB-van deployment target; VST3 is for DAW-based testing/validation against the existing JSFX meter in Reaper.
- **Target platform: Linux for deployment** (broadcast server / OB-van infra), **macOS for development** — the build must work on both.
- **The project is open source.** Test fixtures committed to the repo must be synthetic or freely-licensed — real broadcast archive material can be used for local/internal validation but not published. **Licensing is more nuanced than originally assumed**: moving to Rust does not automatically resolve the VST3 target's GPLv3 obligation (`nih-plug`'s default VST3 export still pulls in GPLv3-licensed bindings, for the same underlying Steinberg-SDK-terms reason as JUCE) — see §8 and `docs/LICENSING.md`.

## 2. What we take from the JSFX, and what we now delegate to a library

The JSFX's actual value isn't its filter/windowing code (that's just BS.1770 done by hand in EEL2) — it's the **behavior on top**: which target/tolerance knobs matter, and how the ratio should behave when there isn't enough signal to trust yet. That's what gets carried forward; the low-level DSP is delegated instead of ported:

- **R128/BS.1770 loudness measurement (K-weighting, channel weighting, momentary/short-term windowing, relative gating) → the `ebur128` crate.** A pure-Rust port of libebur128 (MIT-licensed, maintained by a core GStreamer-rs maintainer), already validated against the official EBU Tech 3341 conformance test vectors — a correctness guarantee the original JSFX never had. It handles arbitrary channel layouts via `EbuR128::set_channel_map()` (`Channel::{Left,Right,Center,LeftSurround,RightSurround,Unused}`), and is streaming/incremental by design (`add_frames_f32()` accepts arbitrary chunk sizes), so the "must work with GStreamer/VST3's variable buffer sizes" requirement is satisfied for free.
- **Two deliberate behavioral deviations from the JSFX, both toward standards conformance rather than away from it — worth stating explicitly rather than silently landing:**
  - Surround-channel weighting becomes the standard BS.1770 **+1.5 dB (≈1.1885×)**, not the JSFX's ad hoc **1.2×** approximation. The difference is small (~0.06 dB) but real.
  - The JSFX's `Clspl *= sqrt(2)` compensation on the mono Dialogue channel was a workaround for how its shared summing window handled a single channel; it's an artifact of that specific implementation, not part of BS.1770. Feeding the mono Dialogue signal into its own single-channel `ebur128_state` (channel mapped as `CENTER`) measures it correctly without needing this hack.
- **What stays custom, because nothing off-the-shelf does it**: the COM/IS ratio itself (`ratio = comShortTermDb − bedShortTermDb`), the target/tolerance banding, and the "hold the ratio steady when there isn't enough valid COM signal yet" gate (the JSFX's `rat_cnt >= 20` freeze behavior). This is reimplemented as a small `RatioEngine` consuming the `ebur128` crate's short-term loudness outputs — a simple valid-signal timer rather than a re-derived gating histogram, since we're no longer trying to bit-match the JSFX's internals, just its *policy*.
- **Not carried forward** (confirmed dead or out of scope): `lufs_d_hist`/`lufs_d_gate`/`lufs_d_db` (write-only dead code in the JSFX, never read elsewhere in the script), the stereo Pearson correlation meter, and all `@gfx` drawing code — parameters are exposed via GStreamer properties / VST3 params, not a from-scratch GUI reimplementation (§8/§11 detail one narrow, later exception: a minimal VST3-only GUI for live meter display).

## 4. Core DSP design

- **`Ebur128Meter`** — a thin wrapper owning one `ebur128::EbuR128` per signal (one for Bed, one for Dialogue), configured with the right channel count/map on stream start via `set_channel_map()` (channel positions read from `GstAudioChannelPosition`/nih-plug's channel-layout metadata, not a fixed pin-index assumption like the JSFX). Audio is pushed in via `push_frames()` (wrapping `add_frames_f32()`) each processing block; `momentary_loudness_db()`/`short_term_loudness_db()`/`integrated_loudness_db()` call straight through to `loudness_momentary()`/`loudness_shortterm()`/`loudness_global()`, sanitizing the non-finite (silence/insufficient-data) case to a `-100.0` sentinel — confirmed against the crate's source that this case surfaces as `Ok(-inf)`, never a distinct error variant, so a plain finite-check is the correct and complete sanitization. This single wrapper replaces the six hand-rolled classes (`Biquad`, `KWeightingFilter`, `SlidingWindowIntegrator`, `GatingHistogram`, `BedLoudnessMeter`, `DialogueLoudnessMeter`) that a from-scratch port would have needed.
- **`RatioEngine`** — the one genuinely bespoke measurement piece. Each ~100 ms tick: reads `bed_meter.short_term_loudness_db()` and `dialogue_meter.short_term_loudness_db()`; tracks a small valid-signal debounce (voice-active for N consecutive ticks, mirroring the JSFX's "enough signal observed" intent without reimplementing its histogram machinery); while valid, `ratio = com_db − bed_db` updates live; while invalid, the last ratio is held. Exposes `RatioResult { ratio_lu, valid, voice_active }`. `valid` is a one-way latch — meter-appropriate ("stop showing blank, show the last known value"), but it means "a ratio was *ever* successfully established," not "COM has signal right now." `voice_active` (real VAD, §6, *this tick* and independent of the latch) exists specifically so control-driving consumers like `AutomixEngine` (§5) can tell the difference — it is one of the two booleans that select the automix state.
- True peak, sample peak, and integrated (relative-gated) loudness are also available for free from the `ebur128` crate if useful as diagnostic/monitoring properties later — not required for the automix control path itself.

**Feed-forward signal flow (this REVERSES the earlier closed-loop design — read this before "fixing" it back):**

Every detector observes the **dry** signal. Bed gain is applied *after* measurement, and nothing downstream of the gain stage is fed back into the control path.

Earlier versions of this document specified the opposite, and called it load-bearing: the Bed meter observed the *already-gained* Bed, on the reasoning that this mirrors a post-fader console meter showing what is actually on air. That reasoning is sound for **metering** and wrong for **control**, and the distinction cost three redesigns to learn. Under feedback the loop cannot observe its own effect until the short-term window has refilled, so every control law had to be slowed to survive a ~3 s measurement lag; speeding it up reintroduced integrator windup and audible pumping, and slowing it down made the mixer feel sluggish and visibly stepped. The architecture, not the tuning, was the problem.

Feed-forward removes it outright. Because reducing the Bed by 1 dB raises the COM/IS ratio by exactly 1 LU, the required reduction is directly computable from the dry levels:

```
required_reduction = target_ratio − (COM_dry − BED_dry)
```

There is no iteration, no convergence behaviour and no stability constraint, because there is no loop. What used to be "one loop that must be slow enough" becomes "several detectors, each free to be as fast as its own window allows" — which is what makes §5.2's cascade possible at all.

The metering argument is preserved separately: `AutomixProcessor::bed_effective_momentary_lufs` reports the dry reading minus the applied reduction, so the GUI still shows what is on air without that value steering anything.

## 5. Automix gain-control design

- **Policy**: automix only *reduces* Bed level (never boosts above unity) — safe ducking semantics.

### 5.1 The state machine

The mixer's behavior is defined by an **explicit four-state machine** (`automix/mix_state.rs`), chosen from the two voice-activity detectors (§6) plus one toggle. This replaced an earlier design in which the same decisions were spread across interleaved, order-dependent branches inside `process_tick` (voice-onset fast-trigger → `!voice_active` release → `valid` gate → tolerance dead-band → hold). That older shape was behaviorally defensible but **unpredictable to reason about and to tune**: it was never obvious which branch would win in a given situation. Naming the four situations and handling each in exactly one place is the whole point.

| COM voice | IS voice | State | Behavior |
|---|---|---|---|
| no | no | `ReleaseToUnity` | release toward unity at the normal Recovery time |
| yes | no | `DuckToTarget` | duck Bed to meet `target_ratio_lu` |
| no | yes | `InterviewPassthrough` | release toward unity at the *faster* Interview recovery time |
| yes | yes | `DuckToOvervoice` | duck Bed to meet the higher `overvoice_ratio_lu` |

- **`DuckToOvervoice`** is the double-talk / "over-voice" case: both the commentator and the Bed carry speech, so COM needs more headroom above the Bed than usual to stay intelligible. `overvoice_ratio_lu` is an **absolute** target (default 8 LU), not an offset on `target_ratio_lu` (default 3 LU) — the two situations are dialed in independently by ear.
- **`InterviewPassthrough`** is `UI.md`'s "voice detector IS": voice on the original (IS) while COM is silent means something on the Bed itself is worth hearing — an interview picked up ambiently, say — so it should not stay ducked from prior programme. It recovers at a fixed multiple of the normal rate (`INTERVIEW_RELEASE_SPEEDUP`) and skips the release hold, since getting back to unity promptly is the whole point. **Always active; there is no toggle** — it is part of the state machine rather than a feature to switch on.
- Release states set `target_reduction_db = 0.0` unconditionally — including when `valid` is still latched true (§4). There's nothing to duck Bed *for* once COM stops talking, and `valid` latching forever means a frozen, increasingly stale `ratio_lu` would otherwise keep the Bed over-ducked through silence.
- **Entering** a ducking state restores `target_reduction_db` to wherever the ratio-driven policy last left it (`last_active_target_reduction_db`) rather than re-converging from whatever the release reached. Short-term loudness has real integration time, so without this the Bed sits under-ducked for seconds after *every* resumed utterance, not just the first of a session. It's a guess, not a measurement — but a good one (same programme, same speaker), and the next correction fixes it if wrong.

### 5.2 Control law: a multi-loop cascade

Three gain stages in cascade, their reductions adding in dB (equivalently, their gains multiplying) — the multi-loop topology used by broadcast dynamics processors, in which several control circuits of differing speed act on the same signal in series. Its defining property is that the effective attack and release times are not configured but **emerge** from how the stages interact, adapting to how the signal evolves. That is why the five separate time parameters earlier designs needed no longer exist.

```
Bed(dry) ─┬─────────────────────► ×g_slow ──► ×g_mid ──► ×g_fast ──► Bed out
          │                          ▲           ▲          ▲
COM(dry) ─┼─────────────────────────────────────────────────┼─────► COM out
          │                          │           │          │
          └──► detectors ────────────┴───────────┴──────────┘
```

Multi-loop designs commonly also place a short delay ahead of the gain stages, so the control circuits see the signal before it reaches the output. **That was implemented here, evaluated on real material and then removed**: the cascade already responds fast enough without it (onset response measured at 0.0–0.1 s), and a lookahead costs exactly its own length in latency. Keeping the signal path strictly unbuffered preserves the element's zero-added-latency property, which the OB-van deployment depends on (§7), and removes a control that earned nothing.

| Stage | Detector | Authority | Ballistics (Speed = 1.0) | Role |
|---|---|---|---|---|
| **slow** | Bed R128 short-term, 3 s | `0 … max_gain_reduction_db` | atk 0.8 s / rel 3 s | programme balance; carries the bulk |
| **mid** | Bed R128 momentary, 400 ms | `±6 dB` trim on slow | atk 0.15 s / rel 0.6 s | tracks Bed dynamics |
| **fast** | Bed K-weighted ~50 ms, **per audio sub-chunk** | `0 … +4 dB` trim on slow+mid | atk 5 ms / rel 0.4 s | catches Bed surges |

Stages are **hierarchical trims**, not three independent controllers: slow states the answer, mid corrects it, fast corrects that. Without the trim structure all three would act on the same error and triple-count it. Bounding each faster stage is also what makes a 5 ms attack safe to have at all — the fast stage cannot run away, because it can never contribute more than its authority.

**Only the Bed is read fast, and this is the single most important detail.** `ratio = COM − BED`, so `required = target − ratio`: when COM gets *louder* the ratio rises and *less* ducking is needed. The event that demands a fast response is therefore a **Bed** surge — a crowd roar burying the commentator — never a COM one. Driving the fast stages from COM as well was implemented and measured, and failed two ways at once:

- At 50 ms a speech signal's "level" is its syllable envelope, so the stage tracked vowels and modulated the Bed at syllable rate.
- A 3 s window over speech-with-gaps measures a systematically quieter COM than a 400 ms window during speech, so the stages disagreed by a near-constant offset and sat fighting: the mid stage parked at −2 to −5 dB while the fast stage repeatedly saturated its clamp.

Reading COM at one stable speed (short-term) for *every* stage fixes both: the stages now measure the same quantity and differ only in how fast they see the Bed move, so they agree in steady state and separate only during a Bed transient. On real commentary this cut total gain movement by 65 % (median 0.88 → 0.31 dB per tick) and fast-stage movement by 70 %.

Supporting details:
- **The fast stage is positive-only.** It may add reduction quickly but never remove reduction the slower stages decided on, because at that time scale a dip in the measurement is usually a gap between syllables rather than evidence the Bed should come up. Clamping at zero is what turns it from an envelope follower into a transient catcher. The cost is a small bias toward over-delivering: measured mean ratio error is **+1.2 LU** against target — erring toward intelligibility, which is the right direction to err.
- **Soft dead-band is gone**; the cascade's own ballistics provide the smoothing a dead-band used to.
- **No voice-onset fast trigger.** The feedback design needed one, because after a gap its measurement was stale; seeding the envelope produced an instantaneous ~19 dB jump. Feed-forward has nothing stale to compensate for, and the cascade covers onsets by itself — mid engages within ~150 ms, fast within milliseconds, slow takes over behind them. Removing the trigger cut the largest single-tick gain movement from **19.4 dB to 8.0 dB** with no loss of onset response.

**Measured on real broadcast material** (60 s commentary over International Sound, `com-is-assist-offline`, channel 1 as COM and channels 2+5 as Bed):

| | value |
|---|---|
| onset response (t63) | **0.0–0.1 s** |
| steady gain movement | median 0.31 dB/tick, slow stage 0.05 |
| ratio held within ±2 LU of target | 67 % of ducking ticks |
| mean ratio error | +1.2 LU |

`speed` is the one remaining timing control: raise it if the mixer feels sluggish, lower it if it breathes.

### 5.3 Timing: why hangover and hold must span a sentence pause

The state machine is only as stable as the booleans driving it. With the original 300 ms VAD hangover and 300 ms hold, measured commentary pauses of ~1.2 s dropped COM to "no voice" in **every inter-sentence break**, flipping to `ReleaseToUnity`, shedding several dB and re-ducking on the next sentence — a swell repeating at sentence rate. Defaults are therefore `VoiceActivityConfig::hangover_seconds = 0.8` and, inside `LoopBank`, a fixed `RELEASE_HOLD_SECONDS = 0.8`: together the Bed does not begin recovering until COM has been quiet for ~1.6 s, so natural pauses pass without movement.

The hold freezes the **entire cascade**, including the fast stage. That is worth stating because the fast stage is stepped from the audio path rather than from the control tick, and an implementation that only froze the tick-driven stages let it keep decaying — measured at up to 1.25 dB of unintended recovery inside the hold window on real commentary. Interview passthrough deliberately skips the hold, since its whole purpose is to reach unity quickly.

Both are deliberately **fixed rather than exposed**. They are properties of speech, not matters of taste, and having the hold as a user control ("Hold time") was part of what made the old parameter surface unmanageable.

### 5.4 Ballistics are emergent, not configured

There is no longer an Attack-Hold-Release envelope on the output, and no attack/hold/release controls. Each stage has its own fixed time constants (table in §5.2) and the *effective* behaviour of the cascade falls out of their interaction: a Bed transient moves only the fast stage, in milliseconds and by a bounded amount; a sustained level change moves all three and the slow stage ends up carrying it. That is the behaviour a multi-loop structure is chosen for — long, gentle attack while the programme is steady, very short attack on an impulsive transient — obtained structurally rather than by tuning.

`EnvelopeDetector` survives as the one shared smoothing primitive, now taking its time constants and time step per call so the three stages can share it while running at genuinely different rates (slow/mid once per ~100 ms control tick, fast once per audio sub-chunk). `GainComputer` is gone.

The single exposed control is **`speed`**, which scales every stage's constants together.

### 5.5 Live reconfiguration

`AutomixEngine::set_config`/`LoopBank::set_config` replace a config in place without resetting any stage's in-flight value or the hold timer — a wrapper can call this every block, cheaply, so host automation (or a dragged slider) actually takes effect. Added after a real bug: VST3's `initialize()` only ever read its parameters once, at plugin load, so raising `max-gain-reduction-db` mid-session silently had no effect. All wrappers now call `AutomixProcessor::set_config` — VST3 every `process()` call, GStreamer on `set_property` (previously a full `ProcessingState` rebuild — see §7).

**No existing library implements this specific ratio-driven ducking policy**, so `AutomixEngine`/`LoopBank` are bespoke — the underlying `EnvelopeDetector` primitive is generic enough that a small permissively-licensed DSP crate could have supplied it, but it's a few lines and hand-rolling it reads better here. The fast stage's K-weighted detector (`automix/fast_loudness.rs`) is likewise bespoke, because R128 defines only 400 ms and 3 s windows and `ebur128`'s are fixed; it deliberately reproduces that crate's K-weighting and channel weighting so its readings sit on the identical LUFS scale.

## 6. Voice-cleaning / VAD sidechain design

**Implemented: real voice-activity detection on *both* the Dialogue (COM) and Bed (IS) sides.** `com_is_assist_core::voice_activity::SileroVad` wraps Silero VAD (a small recurrent ONNX model, vendored in-repo at `crates/com-is-assist-core/assets/silero_vad.onnx` - MIT-licensed, see `docs/LICENSING.md`) run through `ort` (the one place a C++ library - ONNX Runtime itself - sits underneath). Audio is resampled to Silero's required 16kHz mono via `rubato` (pure Rust), fed through in the model's native 512-sample (32ms) chunks with the 64-sample inter-chunk context and recurrent state it expects, and the resulting per-chunk speech probability is smoothed by a hangover timer (`VoiceActivityConfig::hangover_seconds`, **default 800ms**) into a stable `voice_active` boolean. That hangover is effectively "how long a pause still counts as *still talking*", so it has to span a natural **inter-sentence** break, not just an inter-word one — it directly gates the §5 state machine, and at the original 300ms every ~1.2s commentary pause dropped to `ReleaseToUnity` and caused an audible sentence-rate swell (see §5.3).

**Two instances, one per side.** The COM detector gates the ratio/automix loop as before. The **IS detector** (`UI.md`'s "voice detector IS") is fed a **mono downmix of the dry Bed** — Silero is a mono model, and "is anyone speaking anywhere on the Bed" is a whole-Bed question, so averaging the channels is the right reduction. It is deliberately fed the *dry* Bed, before automix gain is applied, so IS detection never depends on how hard the mixer happens to be ducking (which would close an unwanted second feedback path). Together the two booleans select the automix state (§5.1), which is what makes the interview-passthrough and over-voice cases possible at all. Each wrapper owns both instances and passes both into `AutomixProcessor::maybe_run_control_step(com_voice_active, is_voice_active)`. COM fails **open** (treated as always voiced if the detector couldn't be constructed, matching pre-VAD behavior); IS fails **closed** (treated as never voiced), which simply leaves the ordinary duck/release states in play rather than inventing an interview/over-voice state.

That boolean now *is* `RatioResult::voice_active` (see §5/`ratio/ratio_engine.rs`) - it directly replaces what was previously derived from "is COM's short-term loudness above -70dB LUFS?" A loud non-speech noise (room tone, static, another open mic) no longer gets treated as "the target dialogue is present," which the LUFS floor fundamentally couldn't distinguish. `AutomixProcessor` doesn't own the VAD itself - each wrapper (VST3, GStreamer, `com-is-assist-offline`) owns its own `SileroVad` instance (fed dialogue audio directly, independent of Bed's own state/caps-negotiation lifecycle) and passes the resulting `voice_active` into `AutomixProcessor::maybe_run_control_step` explicitly, the same way `automix_enabled` already was - keeping `AutomixProcessor`'s own tests decoupled from needing real speech audio to exercise the ratio/gain logic, while every wrapper still shares the exact same detection implementation (no risk of the *algorithm* diverging, even though each holds its own instance). Fails open (treats COM as always voice-active, matching the pre-VAD behavior) if the ONNX Runtime binary couldn't be obtained at startup, rather than silently never ducking at all.

**Not yet implemented**:
- **Denoising** (`nnnoiseless`, a pure-Rust RNNoise port; `DeepFilterNet`'s native `libDF` + `tract` as an optional secondary path) feeding a `Cleaned` measurement/output source, switchable independently from what's actually sent to Dialogue Out/Mix - none of this exists yet; only the real/dry signal is ever measured or output today. This remains the last substantive M3 item.

## 7. GStreamer element design

Two inputs / three outputs doesn't fit `GstBaseTransform` (1:1) or `GstAggregator` (N:1). The original plan called for `GstCollectPads` to synchronize the two sink pads, but **`gstreamer-rs` 0.25 doesn't provide a safe wrapper for it** (confirmed against the actual crate source: `gstreamer-base`'s `auto/mod.rs` wraps `Adapter`/`Aggregator`/`AggregatorPad`/`BaseParse`/`BaseSink`/`BaseSrc`/`BaseTransform`/`PushSrc` — no `CollectPads`; the raw C struct/functions do still exist one level down in `gstreamer-base-sys`, auto-generated from the C headers, they're just never given an ergonomic wrapper). Rather than reaching for unsafe FFI to use a binding that doesn't officially exist in this ecosystem, `GstComISAssist` is a plain `GstElement` subclass with hand-rolled pad synchronization — the same approach several real elements in the official `gst-plugins-rs` repo use for custom multi-pad sync, since this is the established idiom in the Rust GStreamer ecosystem, not a workaround. Two always/static sink pads (`bed_sink`, `dialogue_sink`) have `chain_function`s; see `Specs/Ressouces/GSTdefinitions.md` for the full pad table.

**Output latency is deliberately decoupled from the automix control rate** (a redesign, not the original v1 shape): the first working version accumulated a full ~100ms tick's worth of both Bed and Dialogue before producing *any* output, batch-processing and pushing all three src pads together. That's simple, but it means real, designed-in output latency (confirmed by a live pipeline with a real-time sink actually glitching from it — see below) tied 1:1 to how often the ratio/gain target gets recomputed, when those two things don't have to be coupled at all. The current design instead:

- Forwards audio to `is_leveled_src`/`dialogue_src` the moment it arrives, in whatever chunk size the upstream happens to deliver — no batching wait, so added latency is effectively zero for these two outputs.
- Applies gain to Bed via a *continuous* per-frame ramp (`com_is_assist_core::automix::apply_ramped_gain_at`/`ramp_value_at`) rather than a per-tick flat scalar — a single logical ramp from one gain value to the next can now span many independently-sized chunks as they arrive, instead of requiring a whole tick to be buffered before any gain can be applied at all. (`apply_ramped_gain`, the simpler whole-block version, is kept for `com-is-assist-offline`, which has no latency concern and processes fixed-size ticks throughout.)
- Forwards `mix_src` as soon as *both* sides have anything to pair (`drain_mix_ready`) — bounded only by however much arrival timing between the two sinks happens to be out of step, not by a fixed wait.
- Still only recomputes the ratio/gain *target* once per ~`TICK_SECONDS` (tracked via frame counters fed by each side, independent of how output happens to be chunked) — that control-rate floor isn't arbitrary: BS.1770/EBU R128 (which `ebur128` implements) itself gates loudness in 100ms blocks internally, so ticking the control loop faster wouldn't yield more frequent loudness information anyway, only more overhead.
- On EOS, `is_leveled_src`/`dialogue_src` each end as soon as their own sink's EOS arrives (no cross-dependency); `mix_src` waits for both, then flushes any still-unpaired tail on the longer side as mix-alone (`flush_remaining_mix_tail`) — normal pairing already drains anything that *can* be paired as it arrives, so a leftover tail at that point just means one side's stream was shorter, not that pairing was skipped.

This means the `LATENCY` query correction noted below is itself now superseded: after this redesign, this element genuinely holds nothing back before forwarding it, so it reports **zero** added latency again — this time because that's actually true, not because of the "no look-ahead ⇒ no latency" conflation the original v1 doc wrongly assumed. Confirmed via `GST_DEBUG=*:4`: the pipeline's `configured latency` dropped by exactly the removed ~100ms contribution once this redesign landed.

- Caps: `bed_sink`/`is_leveled_src` = `audio/x-raw, F32LE, channels=[2,6], layout=interleaved`; `dialogue_*` = same with `channels=1`; `mix_src` mirrors Bed's negotiated layout.
- How mono Dialogue folds into multichannel Bed for `Mix` is exposed as a property rather than hardcoded: `dialogue-mix-mode` (`all-channels`/`front-lr`/`center-if-present`), default `front-lr` (closest to conventional TV commentary practice).
- Properties (see `Specs/GSTdefinitions.md` for the authoritative table): `target-ratio`, `overvoice-ratio`, `max-gain-reduction-db`, `speed`, `automix-enable` (for A/B against raw meter behavior), `divergence`; read-only `current-gain-reduction-db`, `current-ratio-lu`, `voice-active`, `voice-active-is`, `current-mix-state`. Also posts a periodic `GstStructure` bus message (`"com-is-assist-stats"`), following the precedent of GStreamer's own `level` element, for monitoring tools that don't want to poll properties.
- **History, kept for context (superseded by the latency/control-rate decoupling above)**: the original v1 batch-tick design genuinely held ~100ms of audio before producing any output, but still claimed `LATENCY` reports 0 — conflating "no look-ahead" with "no latency." That went uncaught until a live pipeline with a real-time sink (`osxaudiosink`) produced audible periodic glitching that file-based/offline correctness checks couldn't reveal (a synced sink schedules rendering based on the pipeline's total reported latency, so under-reporting it by a tick causes exactly this class of bug). First fix: report the missing ~`TICK_SECONDS` explicitly via a `LATENCY`-query `query_function` override (needed regardless, since the src pads' deliberately-empty `iterate_internal_links` means the default query-forwarding path can't discover upstream latency at all — that part of the fix is still current). The *better* fix, once asked for, was removing the ~100ms buffering delay itself via the decoupling above — so the override now legitimately reports zero again.
- Implemented via `gstreamer-rs`'s subclassing support (`gst::subclass`, `glib::wrapper!`) — the same official, first-party Rust bindings used by upstream `gst-plugins-rs`. Registered as element `"comisassist"` in plugin `"comisassist"`, `GST_RANK_NONE`. Built as a cdylib via `cargo-c` (`cargo cbuild`/`cargo cinstall`), which produces the C-ABI `.so`/`.dylib` + `.pc` file GStreamer's plugin loader expects — the same tooling `gst-plugins-rs` itself uses.

**Four findings from getting a real `gst-launch-1.0` pipeline (not just `cargo build`) to run cleanly end to end, worth keeping on record since none of them are discoverable by inspection alone:**

1. **`iterate_internal_links` must be mapped one-directionally (sink → the srcs it feeds), never bidirectionally, or the graph cycles.** `GstPad`'s default behavior — used internally by things like latency-event redistribution (`gst_pad_forward`) — treats every pad of the opposite direction on an element as linked to every other one; for 2 sinks / 3 srcs that's already a cycle. Declaring the mapping explicitly but *reciprocally* (e.g. `bed_sink` links to `is_leveled_src` *and* `is_leveled_src` links back to `bed_sink`) is still a 2-node cycle on its own, since `gst_pad_forward` walks internal-links as plain undirected adjacency with no visited-set/cycle detection. The fix: sinks report the srcs they feed; all three src pads report an explicit *empty* set (not just an omitted function, which falls back to the buggy default). This makes the whole graph a simple, cycle-free bipartite structure at the cost of srcs being unable to auto-discover their upstream via this generic mechanism — acceptable, since this element's own chain/event functions handle data/event flow directly. Found by tracing a live pipeline hang (infinite latency-event redistribution), not by inspection.
2. **Every buffer this element creates needs a real PTS/duration.** Buffers assembled from raw sample slices (as opposed to ones GStreamer hands you pre-stamped) don't get timestamps for free; without them, downstream elements that care about timing (muxers, `sync=true` sinks) behave incorrectly or hang. Fixed by tracking a running output frame-count and stamping every pushed buffer's `ClockTime` PTS/duration from it.
3. **Real EOS must be deferred until *both* sink pads have reached EOS, not forwarded the instant either one does.** The two sink-side producers (Bed, Dialogue) run at whatever rate their own upstream delivers, and one commonly finishes well before the other (e.g. a short Dialogue file buffers and hits EOS while Bed still has a large backlog). Forwarding EOS on the first arrival both drops the other side's remaining backlog and leaves its pad returning `Err(Eos)` on subsequent pushes, which propagates up as a hard pipeline error. Fixed with a `bed_eos`/`dialogue_eos` flag pair: each side's EOS is recorded and its own buffers drained as far as possible, but the shared src pads only get the real EOS event once both flags are set.
4. **A `queue` element is required directly downstream of each src pad before the next real processing element (e.g. `audioconvert`).** Without it, the pipeline reliably hung with `audioconvert` specifically (confirmed as a genuine hang, not just slow real-time pacing, by running with a timeout far longer than the input file's duration and observing zero progress throughout). Inserting `... ! queue ! audioconvert ! ...` after every one of `is_leveled_src`/`dialogue_src`/`mix_src` resolved it completely and reproducibly — standard practice for thread-decoupling at custom multi-pad element boundaries, and now the documented, required way to consume this element's outputs.

## 8. VST3 wrapper design (phase 2)

**`nih-plug`** over JUCE: a real, actively maintained Rust plugin framework targeting VST3 and CLAP directly, with a bundler (`cargo xtask bundle`), GUI adapters (egui/iced/vizia) if ever needed, and sample-accurate automation support. `nih-plug` is less battle-tested than JUCE for VST3 specifically, but that's an acceptable risk. The core-wrapping structure enforces "no DSP/parameter divergence": both wrappers call into the same `com_is_assist_core::automix::AutomixProcessor` (loudness meters, ratio/gain engines, continuous gain ramp — extracted out of what was originally duplicated logic in the GStreamer element, once the VST3 crate needed the identical control loop) rather than each re-deriving its own copy.

**Bus layout — a fixed single 8-channel bus, not the originally-planned named multi-bus layout.** `Specs/Ressouces/vstDefinitions.md` originally planned 2 named input buses (Dialogue mono, Bed 2–6ch) and 3 named output buses (Dialogue/IS-Leveled/Mix), explicitly flagged as an open item because `nih-plug`'s bus model is "one main input + one main output, plus anonymous aux ports," which doesn't map cleanly onto a named-multi-bus VST3 layout. Implemented instead: **one fixed 8-in/8-out bus** (`main_input_channels`/`main_output_channels = 8`, no aux ports at all) — channels 0-5 = Bed (fixed 6ch, not the dynamic 2-6ch range), channel 6 = Dialogue, channel 7 = unused/silent. This sidesteps the multi-bus open question entirely (no host-compatibility risk from multi-output-bus VST3 plugins) at the cost of always requiring exactly 6 Bed channels rather than negotiating 2-6.

A `mix-dialogue-to-bed` bool parameter (the "bus insert mode" toggle) controls whether output channels 0-5 are leveled Bed alone (matching the GStreamer element's `is_leveled_src` — for inserting directly on a Bed/IS channel strip) or have Dialogue mixed in (matching `mix_src` — for standalone use as the final program bus). When mixed in, Dialogue is restricted to channels 0-2 (Left/Right/Center) only — it never reaches LFE or the surrounds — placed via a `divergence` parameter (`UI.md`'s "Voice divergence": 0% = Center-only, 100% = split Left/Right) using `com_is_assist_core::automix::mix_dialogue_into_bed`'s equal-power pan law, extracted as a shared function for the same "no DSP divergence" reason as `AutomixProcessor`. Channel 6 always carries the dry Dialogue passthrough regardless of the `mix-dialogue-to-bed` toggle. A separate `bypass` bool parameter disables automix entirely (Bed passes through at unity gain) when `true` — deliberately inverted polarity from the GStreamer element's `automix-enable` (`true` = active), matching the conventional meaning of a "Bypass" control.

**Control surface.** The multi-loop redesign removed five timing parameters (`adaptation-ms`, `attack-ms`, `hold-ms`, `release-ms`, `interview-release-ms`) because the cascade's ballistics are emergent (§5.4), and replaced them with one **`speed`** macro. The full VST3 surface is now `target-ratio`, `overvoice-ratio`, `max-gain-reduction-db`, `speed`, `bypass`, `mix-dialogue-to-bed`, `divergence` — seven, down from twelve, with the five that were hardest to reason about gone. GStreamer mirrors them (seconds, and `automix-enable` in place of `bypass`).

**Resolved: a custom GUI, covering both live meters and the parameter controls.** Live meters can't be exposed as parameters — `nih-plug`'s parameter setter (`ParamMut`) is deliberately `pub(crate)`, so a plugin cannot programmatically update its own parameter's displayed value from `process()` — that's why a custom GUI exists at all (superseding the original "no custom GUI, parameters only" non-goal from §11, now revised). Implemented via `nih_plug_egui`: a `Meters` struct of `Arc<AtomicF32>` fields, written from `process()` only while the editor is open and read each frame in `editor()`. Redesigned (visual/layout only, no DSP change) into a tall, professional-bargraph-style meter bank on the left of the window with all parameter controls on the right — loosely modeled on the original Reaper JSFX reference meter and professional loudness-meter hardware (e.g. RTW), not on peak-meter-ballistics standards. Four vertical bar meters, left to right: gain reduction, IS, ratio, COM — each 420px tall, narrow, and drawn with a fixed-pitch segmented-gap overlay for a discrete-LED look — sharing one visual language (filled rect over a dark background rect), gain reduction/IS/COM each paired with an adjacent tick-mark scale:
- **Gain reduction** — its own standalone bar (not carved out of the IS bar, as an earlier iteration did), fills top-down from 0 to `applied_gain_reduction_db()` against a fixed 0-48dB range, red, with its own top-down scale. Made standalone specifically so gain reduction and ratio can both be read clearly at a glance while tuning attack/hold/release by ear.
- **IS (Bed)** — fills bottom-up, cyan, fixed -60..0 LUFS range, to `AutomixProcessor::bed_momentary_lufs()` (pre-gain, via a second `Ebur128Meter` kept separate from the closed-loop control meter — see that method's doc comment).
- **Voice-activity LEDs and state readout** — a green/grey LED under the COM bar *and* under the IS bar (the latter unblocked by the IS-side VAD now existing, §6), plus a live text readout of the current `MixState` in the controls column. With behavior now defined entirely by which of four states the mixer is in, showing that state directly is the fastest available answer to "why is it doing that right now?" — considerably more legible than inferring it from the meters.
- **Ratio** — positioned between IS and COM, drawn as a bar spanning the gap between Bed's *effective* level and `bed_effective_momentary_lufs() + display_ratio_lu` on the *same* LUFS scale (LU is literally a LUFS difference), colored by a four-state GUI-only read of where `AutomixProcessor::applied_ratio_lu()` — the ratio the control is actually achieving, i.e. the dry ratio plus the applied reduction — sits relative to whichever target is active (`AutomixProcessor::active_target_ratio_lu`, so the over-voice state is coloured against its own higher target): grey when negative (COM quieter than IS), red when under target, green on target, orange above it. The bar's *height*, however, uses a separate `AutomixProcessor::display_ratio_lu()` (dialogue momentary minus Bed's *effective* momentary, floored at 0) rather than `applied_ratio_lu` directly — the two are computed from different meters/time-constants entirely, so using `applied_ratio_lu` (or anchoring against Bed's raw pre-gain level) made the bar inconsistent with what's actually audible — `display_ratio_lu` fixes that by matching what the ear (and the IS/COM bars) actually perceive. Floored at 0 rather than signed: COM having a brief natural gap below Bed's effective level isn't itself alarming and isn't worth showing as a negative "distance."
- **COM (Dialogue) momentary loudness** — same as IS, orange, via `AutomixProcessor::dialogue_momentary_lufs()` (never gained, so no pre/post distinction on this side).

Integrated LUFS was tried in an earlier iteration and dropped as an unneeded simplification. Parameters (target ratio, max gain reduction, attack/hold/release, voice divergence, bypass, mix-dialogue-to-bed) are exposed directly in the same window via `nih_plug_egui`'s `ParamSlider` (and a hand-rolled `ui.checkbox` + `ParamSetter` pairing for the two bool params, since `nih_plug_egui` has no built-in bool widget) — still routed through the host's automation via `ParamSetter`, not a GUI-only shadow state, so host automation/undo continues to work identically. See `Specs/vstDefinitions.md`.

Since `nih-plug`'s `Buffer` is planar (one slice per channel) while `com_is_assist_core` works in interleaved audio (matching the GStreamer element's convention), the VST3 wrapper de-interleaves Bed into a scratch buffer before calling into `AutomixProcessor` and re-interleaves on the way out — the only real translation layer needed.

**Building/bundling**: `nih-plug` doesn't publish to crates.io — it's a git dependency (`nih_plug = { git = "https://github.com/robbert-vdh/nih-plug.git" }`). Bundling uses `nih-plug`'s own `cargo xtask bundle` mechanism: a small `xtask` crate (workspace member, wraps `nih_plug_xtask::main()`) plus a `.cargo/config.toml` alias and a root `bundler.toml` naming the plugin. `cargo xtask bundle com-is-assist-vst3 --release` produces a real, correctly-signed `.vst3` bundle (confirmed: valid arm64 Mach-O binary, loadable bundle structure) with no additional tooling beyond what `nih-plug` itself provides.

**Licensing correction (verified directly, don't assume otherwise):** moving to Rust does **not** resolve the VST3 target's GPLv3 obligation. `nih-plug` itself is ISC-licensed, but its VST3 export path (`nih_export_vst3!()`) depends on the `vst3-sys` crate, which is GPLv3 — because it wraps Steinberg's VST3 SDK under the SDK's dual-license terms. (Steinberg did release VST3 SDK 3.8.0 under MIT, and a newer, permissively-licensed `vst3` crate — MIT/Apache-2.0 — now exists as an alternative binding, but `nih-plug`'s default export doesn't use it yet. Worth revisiting once/if that changes, not resolved now.) So the project's overall license should still be **GPLv3** for the reasons in `docs/LICENSING.md`, specifically scoped to the VST3 target — the GStreamer- and core-DSP-facing parts of the stack are plausibly more permissively licensable (most of the Rust crates involved are MIT/Apache-2.0) if that's ever worth splitting out, but that's a future decision, not this one.

## 9. Build system

Cargo workspace (`Cargo.toml` at the repo root, `resolver = "2"`). Cargo replaces CMake entirely — nothing meaningful is lost:

- Dependency fetching: Cargo's registry deps replace CMake's `FetchContent` (previously used only for Catch2) — no fetch-workaround needed at all now that `cargo test` is built in.
- `ebur128`/`hound` are pure-Rust crates.io dependencies — no `pkg-config`/Homebrew package needed for either (a simplification versus the old `libebur128`/`libsndfile` C-library story).
- Build-time toggles (previously `COMIS_BUILD_GSTREAMER`/`COMIS_WITH_DENOISE_RNNOISE`/etc. CMake options) become Cargo features on `com-is-assist-core` plus workspace member selection (`cargo build -p com-is-assist-gstreamer`).
- GStreamer itself is still a C library on the target — `gstreamer-rs` uses `pkg-config` internally in its own build script (`gstreamer-1.0`/`gstreamer-base-1.0`/`gstreamer-audio-1.0`), so the OS-level prerequisite (`brew install gstreamer` on macOS / apt on Linux) is unchanged, it's just no longer hand-wired in project CMake.
- **`cargo-c`** (`cargo cbuild`/`cargo cinstall`) is the one genuinely new piece of tooling, needed only for `com-is-assist-gstreamer`'s cdylib (see §7) — smoke-tested via a build-pipeline bootstrap element and confirmed working end to end (`gst-inspect-1.0` sees it, a live `gst-launch-1.0` pipeline passes audio through byte-identical). Two concrete gotchas found, now fixed and worth remembering: (1) `cargo cbuild` requires a `capi` Cargo feature to exist even though a GStreamer plugin has no C header to gate behind one — an empty `[features] capi = []` satisfies it; (2) `BaseTransformImpl`'s `PASSTHROUGH_ON_SAME_CAPS = true` routes matching-caps buffers through a separate `transform_ip_passthrough` hook that GstBaseTransform's C base class has no usable default for, which panics at runtime the moment input/output caps match (the common case) unless that hook is also implemented — setting it `false` (always use `transform_ip`) sidesteps this until/unless the passthrough optimization is actually needed.
- **ONNX Runtime (for Silero via `ort`) is not a target/runtime dependency** - resolved differently than originally planned here. `ort`'s `download-binaries` feature fetches a prebuilt ONNX Runtime *static* library at build time (cached after the first fetch, so only the build machine ever needs network access for it, once) and statically links it directly into the compiled binary - verified with `otool -L` against the actual built VST3/GStreamer artifacts, which show no `libonnxruntime` dependency at all. No Homebrew package, no target-side install step, and the deployed artifact runs fully offline. (DeepFilterNet's primary path, `libDF` + `tract`, still needs no such dependency either way, since `tract` is pure Rust - not yet implemented, see section 6.)
- RNNoise's replacement, `nnnoiseless`, is a plain crates.io dependency (pure Rust) — no git submodule, no vendoring. Not yet implemented (section 6).
- Silero's small `.onnx` vendored in-repo (MIT-licensed, redistributable, `crates/com-is-assist-core/assets/silero_vad.onnx`, embedded via `include_bytes!`); larger DeepFilterNet models would be fetched via a pinned-SHA256 build step rather than committed, if/when that path is built.
- macOS dev loop documented in `docs/DEV_SETUP_MACOS.md`: `rustup` (toolchain) + `brew install gstreamer gst-plugins-base gst-plugins-good cargo-c` (no `onnxruntime` package needed - see above), then standard `cargo build`/`cargo test`, `GST_PLUGIN_PATH` pointed at the built cdylib for `gst-launch-1.0` testing.

## 10. Testing / validation strategy

1. **Golden-reference comparison against the JSFX meter** — now a *ballpark sanity check*, not a bit-exact port validation, since §2 documents two deliberate standards-conformance deviations (surround weight, no sqrt(2) mono hack). Add a debug-logging JSFX fork (`tests/golden/reaper/..._LOGGING.jsfx`, never touching the real reference file) dumping per-tick LUFS/ratio values to CSV, and compare against `com-is-assist-offline`'s output with a tolerance wide enough to absorb the known, intentional deltas (document the expected delta magnitude somewhere durable so a widening tolerance isn't mistaken for a bug later). Because the project is open source, all fixtures used here must be synthetic or freely-licensed audio — not real SRF broadcast archive material, which can still be used for local/internal validation but never committed to the public repo.
2. **Conformance testing "for free"**: since the `ebur128` crate is already validated against the official EBU Tech 3341 test vectors, running those same public vectors through `Ebur128Meter` gives a real standards-conformance check that the original JSFX never had — worth adding as its own `cargo test` target independent of the JSFX comparison.
3. **Unit tests (`cargo test`)**: `Ebur128Meter` against known-level synthetic test tones (expected LUFS within tolerance — already validated at M1: a 400 Hz full-scale sine measures ≈-3.7 LUFS), `RatioEngine` hold/valid-signal timing, `MixState`'s full truth table, `AutomixEngine` step-response/dead-band/max-reduction/attack-vs-release/per-state behavior, `DialogueAnalysisChain` passthrough bit-exactness with null backends.
   - **Two tests specifically guard against the pumping regression** (§5.2), since it is the defect this design exists to fix and it would be easy to reintroduce: one holds the measurement deliberately stale and asserts the correction is worked off **continuously** (no single tick may move the gain by ≥1 dB) without winding up; the other runs a simulated closed-loop plant (first-order lag approximating the 3 s window) and asserts the reduction settles on target, peaks below 18 dB chasing 12 dB, and is flat to within 0.5 dB once settled. A third asserts `adaptation_seconds` actually governs responsiveness, since it is the user-facing speed control.
4. **Empirical pumping measurement**: `com-is-assist-offline` emits per-tick CSV including `com_voice_active`, `is_voice_active`, `mix_state` and `gain_reduction_db`. Running it over a speech-with-gaps-over-loud-Bed fixture and counting direction reversals / total gain churn is how the §5.2 table was produced; re-run it after any change to the control law or the timing defaults.
5. **GStreamer integration**: `gst-launch-1.0` smoke pipelines, state-change and mismatched-pad-EOS tests (`GstCollectPads` sync is a real risk area), bit-exact passthrough check on `dialogue_src`, live property-adjustment tests via stats bus messages.
6. **Cross-format parity** (once VST3 exists): render identical fixtures through both wrappers, diff outputs — empirical proof the shared-core requirement actually holds.

## 11. Milestones

- **M1 (done, in Rust)** — Wire up the `ebur128` crate (`Ebur128Meter`) + build `RatioEngine`'s hold/valid-signal logic + `com-is-assist-offline`. Exit: EBU conformance vectors pass (inherited from the crate's own test suite); `cargo test` reproduces the exact numeric contract (e.g. the 400 Hz sine → ≈-3.7 LUFS check) and the offline CLI matches the expected ratio-hold behavior on a synthetic bed+dialogue fixture.
- **M2 (done, then superseded)** — Gain automation engine. Originally a single Attack-Hold-Release envelope driven by a closed-loop measurement. That shape was replaced by the feed-forward multi-loop cascade (§4/§5.2) after three attempts to tune the single loop each fixed one symptom and exposed another; `GainComputer` and the AHR stage no longer exist. Exit criteria (no pumping, no flutter, converges) are unchanged and are now met by the cascade.
- **M3 (mostly done)** — VAD/denoise sidechain. **Done**: real voice-activity detection (Silero via `ort` + `rubato` resampling) on **both** the COM and IS sides (§6); the VAD-onset fast-trigger (now a state-entry behavior, §5.1); and the interview-passthrough override (now the `InterviewPassthrough` state rather than a separate override path, §5.1). **Not done**: the denoise path (`nnnoiseless`/DeepFilterNet). Exit (remaining): A/B on spill-contaminated material shows fewer false bed-reduction triggers once denoising cleans the COM measurement path.
- **M4** — GStreamer element (`gstreamer-rs`, built via `cargo-c`) wrapping M1–M3 (pads, properties, stats messages, registration, integration tests). Exit: stable multi-minute runs on real broadcast-style material, macOS dev + target Linux. The macOS→Linux question is resolved as "build natively on Linux," not `rustc --target` cross-compilation: `.github/workflows/build-linux.yml` runs `cargo test` + `cargo cbuild` on an actual Ubuntu runner (matching the deployment target) and smoke-tests the built plugin with `gst-inspect-1.0`, uploading the resulting `.so` as a build artifact.
- **M5** — VST3 wrapper (`nih-plug`) around the same core, validated in Reaper against the original JSFX, cross-format parity test passes.
- **M6 (stretch)** — look-ahead/latency-compensated attack, optional cleaned-audio-to-output routing, DeepFilterNet quality evaluation.

**Non-goal, revised**: no custom GUI at all for the GStreamer element — parameters stay exposed via GObject properties only, since Strom/gst-launch pipelines have no host GUI to embed one in anyway. For the VST3 wrapper (§8), a `nih_plug_egui` GUI now exists covering both live meters (gain reduction, R128 IS/Comm loudness, COM/IS ratio) and the parameter controls themselves — the original "parameters only, no GUI controls" restriction was dropped once a GUI existed regardless (for the meters), since duplicating parameter controls in it via `ParamSlider`/`ParamSetter` costs little and matches what most VST3 plugins provide. Host automation/undo/preset-recall behavior is unaffected — every control still round-trips through `ParamSetter`/`ParamMut`, not GUI-only state.
