# VST definitions

VST3 bus/parameter definitions for the Com-IS-Assist plugin, built with `nih-plug` (see `Specs/TechnicalConcept.md` section 8). Implemented in `crates/com-is-assist-vst3`.

## Bus structure

**Bed on the main bus, COM on a mono sidechain, one plugin per bed format.** One binary (`Com-IS-Assist.vst3`) exports four plugins that differ only in the bed layout. Each has exactly one fixed layout: main in = main out = the bed, plus one mono aux input (`COM`). The sidechain is input-only, so COM is never passed through; it already has its own path in the host.

| Plugin | Class ID | Main bus (in = out), channel order | Duck-depth groups |
|---|---|---|---|
| Com-IS-Assist 2.0 | `ComISAssistDuk20` | 2: L R | none (one pair has nothing to distribute across) |
| Com-IS-Assist 5.1 | `ComISAssistDuck1` (the old 8-channel plugin's ID, so existing sessions reopen on it) | 6: L R C LFE Ls Rs | Front L/R, Center, LFE, Surround L/R |
| Com-IS-Assist 5.1.4 | `ComISAssistDk514` | 10: L R C LFE Ls Rs Ltf Rtf Ltr Rtr (VST3 `k51_4`) | the 5.1 groups plus Top Front L/R, Top Rear L/R |
| Com-IS-Assist 7.1.2 | `ComISAssistDk712` | 10: L R C LFE Ls Rs Sl Sr Tsl Tsr (VST3 `k71_2`) | the 5.1 groups plus Side L/R, Top Side L/R |

On 7.1.2, "Surround L/R" is VST3's Ls/Rs, which on that layout are the rear pair. They are the same speakers as Ls/Rs on 5.1, so they keep the same control. For loudness, the side pair (Sl/Sr, M±090) gets BS.1770's +1.5 dB surround weight, and the rear pair (M±135) does not.

**Why one plugin per layout, not one plugin with several layouts.** nih-plug can offer several `AUDIO_IO_LAYOUTS` from one plugin, but the host then decides which one to use. Hosts differ in whether they renegotiate a VST3's layout to the track width, and a wrong choice fails silently: a 5.1 bed gets processed as stereo. Fixed per-format plugins avoid that. They also let each format hide parameters it has no channels for: those are non-automatable and absent from the host's list. All four share the same code; they are one generic type (`ComISAssist<F: BedFormat>`).

**Exact speaker arrangements.** Each plugin reports exactly one VST3 arrangement for its main bus, and accepts only that one from the host: `kStereo`, `k51`, `k51_4` or `k71_2`. The sidechain is `kMono`. Because 5.1.4 and 7.1.2 are both ten channels, each plugin declares its arrangement itself (`Vst3Plugin::VST3_MAIN_BUS_ARRANGEMENT`), so the 5.1.4 plugin refuses a 7.1.2 track and the reverse, rather than processing it with the wrong channel roles. Upstream nih-plug can't do this: it matches on channel count only, and it reports 10 channels as a generic mask. It also had an index bug that refused every main + sidechain request; the patch fixes that too. The build therefore uses a patched copy, `vendor/nih_plug` (see `PATCHED.md` there), wired in through `[patch]` in the workspace `Cargo.toml`.

An unconnected sidechain reads as silence, so the bed stays at unity rather than raising an error.

### `mix-dialogue-to-bed` parameter ("bus insert mode")

A bool parameter selecting what the main output bus carries:

- **On** (default): Left/Right/Center carry the leveled Bed with Dialogue mixed in, using the `divergence` pan law below. On 2.0, Dialogue goes to L and R at equal power, with no divergence control. Every other channel (LFE, surrounds, sides, heights) is leveled Bed only; Dialogue never reaches it.
- **Off**: every output channel is the leveled Bed alone, with Dialogue not folded in anywhere. This matches `is_leveled_src`, for inserting directly on a Bed/IS channel strip where Dialogue is summed in separately downstream.

Dialogue is never passed through on a channel of its own: it arrives on the sidechain, which is input-only, and already has its own path in the host.

### `divergence` parameter ("Voice divergence", `UI.md`)

0-100%, only has an effect while `mix-dialogue-to-bed` is on. Controls how Dialogue is placed across Left/Center/Right when mixed in, via `com_is_assist_core::automix::mix_dialogue_into_bed`'s equal-power (constant-power) pan law:

- **0%**: Dialogue is Center-only.
- **100%**: Dialogue is split across Left/Right only, each at `1/sqrt(2)` (~-3dB) so the total acoustic power matches Center-only rather than growing louder as it spreads — the standard constant-power crossfade, not a linear one.

## Parameters

- `target-ratio` — LU, whole-dB steps, displayed as **"IS Voice Ratio"**. How far COM must sit above IS while COM alone has voice (`MixState::DuckToTarget`). The parameter *id* deliberately stays `target-ratio` even though the display name changed: the id is what host automation lanes and saved presets key off, so renaming it would silently break existing sessions.
- `overvoice-ratio` — LU, 0-24, default 13. The **absolute** (not additive) distance required while COM *and* IS both have voice (`MixState::DuckToOvervoice`) — the double-talk case needs more headroom for COM to stay intelligible. See `Specs/TechnicalConcept.md` section 5.1.
- `max-gain-reduction-db` — dB
- `com-gate-lufs` ("Voice Detect Gate") — LUFS, -70..-10, **default -32 (engaged)**. Guard band on COM voice detection: reported speech on COM is ignored while COM's own momentary loudness is below this. Stops bed crosstalk in the commentary mic from ducking the bed against its own bleed - the detector cannot tell spill from speech by content, because it *is* speech, but it is reliably far quieter. Typical useful settings are 20-30 dB below the commentator's own momentary level. It shipped at -70 (the bottom of the range, i.e. doing nothing) while the feature was new; the default was later moved to -32, since a gate parked at its floor protects nothing and crosstalk ducking the bed against its own bleed is the failure it exists to prevent. See `Specs/TechnicalConcept.md` section 6.
- `attack-ms` ("Attack") - 20-600 ms, default 150, skewed so the default sits at the slider's exact centre (`centred_skew`). The **mid** stage's attack, with the slow and fast stages' attacks scaled by the same ratio. See `AutomixEngineConfig::attack_seconds` and `Specs/TechnicalConcept.md` section 5.2.
- `release-s` ("Release") - 0.4-12 s, default 3, centred likewise. The **slow** stage's release, with the mid and fast stages' releases scaled by the same ratio. Both ranges are the old `speed` macro's 8x-0.25x, which they replace; `speed` scaled both directions by one factor and could not change one without the other.
- `tolerance-lu` ("Tolerance") - 0-6 LU in 0.5 steps, default 2. The dead band of the mid and fast stages: deviations from the slower stages' answer within it are ignored. It exists because those stages ride the peaks of a fluctuating bed, which made subtle reductions busy and roughly twice as deep as needed - see `Specs/TechnicalConcept.md` section 5.2a for the measurements. Also sets the ratio meter's green band (at least `RATIO_METER_MIN_GREEN_BAND_LU`, 1 LU).
- `fast-stage` ("Fast Stage") - bool, default on. Off takes the millisecond stage out of the cascade (`AutomixEngineConfig::fast_stage`), for comparing the result with and without it. Shown as a checkbox in the controls grid.

- `duck-depth-front`, `duck-depth-center`, `duck-depth-lfe`, `duck-depth-surround`, `duck-depth-top-front`, `duck-depth-top-rear`, `duck-depth-side`, `duck-depth-top-side` ("Duck Depth Front L/R / Center / LFE / Surround L/R / Top Front L/R / Top Rear L/R / Side L/R / Top Side L/R"). All eight exist on every format, but each format hides the groups it has no channels for (see the table above) — factor 0-1 in 0.05 steps, **default 1**, displayed as a **ratio**: `1:1` takes the computed gain reduction in full (6 dB of ducking reduces those channels by 6 dB), `1:0` takes none of it. See `com_is_assist_core::automix::DuckDepth`.

  A **distribution** control, not a second gain stage. The reduction is still computed once, from the whole Bed's loudness, by the state machine and the cascade; these only decide how that one answer is spread. Every group at `1:1` reproduces the pre-feature behaviour exactly, which is the default. It exists because the Bed is not homogeneous - ducking the surrounds as hard as the front throws away atmosphere that was never competing with the commentator, and the LFE carries no intelligibility to protect at all.

  **Scaling is linear in dB, not in linear gain.** At `1:0.5` a group takes half the *decibels*, so the relationship between groups holds at every reduction depth rather than drifting with the size of the reduction - which is what lets the number mean something fixed.

  **A ratio rather than a percentage**, because that is how this kind of relationship is read, and how the control was described when it was asked for. It needs a parser as well as a formatter (`with_string_to_value`): nih-plug would otherwise render `0.50` and then fail to read back the `1:0.50` it had just displayed. The parser accepts a bare factor too, so typing either form works. A per-group **max duck in dB** was considered as the alternative - a ceiling, like a gate's Range, consistent with the existing `max-gain-reduction-db` - and rejected: it would make the groups duck identically until one hit its limit, where the ratio keeps them proportional throughout.

  **Channel pairs, not individual channels.** Left and Right must duck by the same amount or the difference is heard as the stereo image sliding sideways, and the same goes for the surround, side and height pairs. An earlier revision exposed all six 5.1 channels positionally and was dropped for that reason - and because which role sits at a given stream position depends on the channel count, so positional names mislabel themselves on every layout but the widest. `DuckDepth::per_channel_for` resolves groups to channels in the core, against the same `BedLayout` map the loudness meters use, so both wrappers inherit one definition.

- `bypass` — `true` disables automix entirely (Bed passes through at unity gain); `false` (default) is normal operation. Named for the conventional meaning of a "Bypass" control in a DAW plugin, which is why its polarity is inverted from the core's `automix_enabled`.
- `mix-dialogue-to-bed`, `divergence` — see above

**Not exposed anywhere**: the individual per-stage time constants (Attack and Release scale them per direction), the stages' authorities, and the release hold. These are properties of speech and of the R128 window structure rather than matters of taste - see `Specs/TechnicalConcept.md` sections 5.2/5.3. Real voice-activity detection is implemented on **both** sides (`com_is_assist_core::voice_activity::SileroVad`, see `Specs/TechnicalConcept.md` section 6) but always-on: neither detector has an on/off parameter. The IS detector is fed a mono downmix of the dry Bed; the two behaviours it unlocks (fast recovery when only IS has voice, and the higher `overvoice-ratio` when both do) are part of the state machine rather than switchable features.

**Every control row goes through `control_grid`**, including the two that sit alone between the dividing rules, so all of them share one geometry: the same label column, the same `CONTROL_LABEL_GAP` (12px), and - because `Grid` installs its spacing on the `Ui` the cells inherit - the same gap inside `ParamSlider` between its bar and its value box.

Those two rows were originally laid out by hand with `ui.horizontal`, inheriting egui's default 8px and sitting 4px left of every other slider. Matching the grid by setting `item_spacing.x` on the row is **not** the fix, and was tried: `ParamSlider` builds its own inner `horizontal`, so zeroing the row's spacing to control the label gap also closes the gap between the slider and its value readout, leaving those two rows visibly cramped. Giving them a `Grid` of their own is what makes them identical by construction.

**Every level control but `tolerance-lu` steps and displays in whole units.** `target-ratio`, `overvoice-ratio`, `max-gain-reduction-db` and `com-gate-lufs` (dB/LU) and `divergence` (percent) all use `with_step_size(1.0)` *and* `formatters::v2s_f32_rounded(0)` - the step size alone still renders "3.0 LU", so the formatter is what actually removes the decimal. A fraction of a dB, or of a percent of pan position, is below the resolution of the decision being made with these controls. `tolerance-lu` steps in half LU, because its useful settings sit between 1 and 3, where a whole LU is too coarse. `attack-ms` and `release-s` are continuous: their ranges span a factor of 30, where a fixed step that read sensibly at the bottom would be far too fine at the top. Attack displays whole milliseconds; Release shows one decimal below 10 s and none above, since a tenth of a second matters at 0.4 s and nothing at 12 s.

`process()` publishes the detectors' answer with `AutomixProcessor::set_voice_activity` *before* `process_bed`, so a state change reaches the fast stage on the same block rather than at the next ~100ms control tick - see `Specs/TechnicalConcept.md` section 9b.

**The audio thread allocates nothing and runs no inference.** `process()` works out of three buffers preallocated at `initialize()` (`interleaved_bed`, `dialogue_scratch`, `mono_bed_scratch`) rather than a `vec![]` per block, de-interleaves and computes the IS detector's mono downmix in the same pass, and hands both VADs their audio through `BackgroundVad` - a bounded copy into a lock-free ring, with the ONNX inference on a worker thread. See `Specs/TechnicalConcept.md` section 9a for the measurements that drove this; the short version is that the worst block went from 204% of a 64-sample real-time budget to 3.5%.

**Live updates**: `process()` calls `AutomixProcessor::set_config()` every block with the current live values of every parameter above, so changing any of them (a host automation lane, or dragging the GUI's `ParamSlider`s) takes effect immediately. Fixes a real bug: `initialize()` only reads these parameters once, at plugin load - without the per-block refresh, raising `max-gain-reduction-db` past its 24dB default toward its 48dB ceiling mid-session had no effect, since `AutomixEngine` kept using whatever config it was constructed with. See `Specs/TechnicalConcept.md` section 5.

## GUI (custom, meters + controls)

Resolved: `nih-plug`'s parameter setter (`ParamMut`) is deliberately `pub(crate)` - a plugin cannot programmatically update its own parameter's displayed value from `process()`, so live meters can only be shown via a custom GUI reading shared atomic state directly. Once a GUI existed for that reason, it also grew to expose the actual parameter controls - see `Specs/TechnicalConcept.md` section 8/11 for why the original "meters only, no GUI controls" scoping was dropped.

Implemented via `nih_plug_egui` (`create_egui_editor`):

**Overall layout**: a tall, professional-bargraph-style meter bank on the left, all parameter controls in a single column on the right (`ui.horizontal` splitting a left `ui.vertical` meter bank from a right `ui.vertical` controls panel, separated by `ui.separator()`) - modeled loosely on the original Reaper JSFX reference meter and professional loudness-meter hardware (e.g. RTW's product line), not on any specific peak-meter ballistics standard: this is a **look-and-scale-only** redesign, the underlying R128/EBU loudness measurement, DSP, and value semantics are unchanged from the description below.

**No numeric readouts under the bars.** The per-meter dB/LUFS/LU figures were removed: the scale beside each bar already gives the value to the precision anyone reads a meter at, and four live numbers changing at tick rate drew the eye away from the bars themselves. Their removal is also what lets each metered column be *exactly* bar + gap + scale, which is what makes the column spacing read evenly (see `METERED_COLUMN_WIDTH`).

**Meters** - a `Meters` struct of atomics is written from `process()` (only while the editor is actually open, to keep the audio thread's hot path clear the rest of the time) and read from the `editor()` closure each GUI frame. Each bar is `METER_BAR_HEIGHT` (420px) tall and narrow (`METER_BAR_WIDTH`, 20px), drawn as a continuous fill. (An earlier iteration overlaid a fixed-pitch segmented-gap pattern for a discrete-LED-bargraph look; it was dropped once the bars grew to their current height, where the segmentation read as texture rather than as segments and competed with the gain-reduction block and the gate shading drawn over the same fill.) Layout, left to right: gain reduction (+ its own scale), IS (+ its own scale), ratio, COM (+ its own scale) - gain reduction sits immediately next to IS/ratio specifically so the two values the user tunes by ear against each other are easy to read side by side. Each loudness bar gets its own scale immediately to its right, as close as the tick text allows, rather than one shared scale off to a single side. Each meter column is a fixed width (`fixed_width_column`, content centered within it) so a column's width never depends on what is drawn in it - originally this stopped columns shifting as a live numeric label's text length changed ("-inf LUFS" vs "-6.3 LUFS"); those readouts have since been removed, but fixed widths remain what the bar-gap arithmetic below is computed against. `ui.spacing_mut().item_spacing.x = 0.0` on the row disables egui's automatic inter-widget spacing so every gap in the row is exactly what's asked for via `ui.add_space`, not that plus an extra unrequested default gap. All bar meters share the same visual language (a filled rect over a dark background rect, drawn directly via `egui::Painter`):
- **Gain reduction**: a standalone bar (`gain_reduction_meter`), fills top-down from 0 to `applied_gain_reduction_db()` against a fixed 0-36dB range (`GAIN_REDUCTION_METER_MAX_DB` - still above the 24dB default ceiling, but no longer stretched to the 48dB maximum, which compressed normal working levels into the top third of the bar), red, with its own top-down scale. Standalone rather than carved out of the IS bar (an earlier iteration's approach) so both gain reduction and ratio can be read clearly at a glance while tuning, per explicit user request.
- **IS (Bed)**: fills bottom-up (the conventional level-meter orientation) to `bed_momentary_lufs()` - the dry/incoming programme level, on a fixed -60..0 LUFS display range, in the control accent colour (see below). Since the redesign made the control path feed-forward, this is the *same* meter the control loop reads, so the displayed IS level and the controlled one can no longer disagree (they were deliberately separate meters under the old closed-loop design, which needed a post-gain meter for control and a dry one for display).
- **Ratio**: positioned between the IS and COM bars, matching the original JSFX reference meter's layout. Rather than an independent bar with its own arbitrary range, it's drawn as a bar spanning the gap between Bed's *effective* (post-reduction) level and that same level plus `display_ratio_lu` on the *same* shared LUFS scale as the loudness bars (LU is literally a difference of LUFS values, so this is a valid, not just visually convenient, choice). **Uses `AutomixProcessor::display_ratio_lu()` for the bar's height/label, *not* `applied_ratio_lu()`** - the two answer different questions. `display_ratio_lu` is dialogue momentary minus Bed's *effective* momentary (`bed_effective_momentary_lufs()`, the dry reading minus the currently-applied reduction), so it matches what is actually audible and lines up with the bars drawn either side of it; `applied_ratio_lu` is the short-term ratio the control path works in, plus the applied reduction - the right number to judge "are we on target", the wrong one to draw a bar between two momentary meters. `display_ratio_lu` is also floored at `0.0`: a negative "distance" isn't meaningful to show here (COM briefly dipping below Bed's effective level during normal speech gaps isn't itself alarming). **The bar's *colour* reads where `applied_ratio_lu()` (the signed, achieved ratio - deliberately not the floored display value, which can never be negative, so the grey state would be unreachable) sits relative to the active target**: grey when negative (COM currently *quieter* than IS - a distinct situation from "not loud enough yet"), red when positive but under target by more than the green band, green otherwise. The band is the **Tolerance** control's value, floored at `RATIO_METER_MIN_GREEN_BAND_LU` (1 LU) so it stays readable at Tolerance 0: the meter's "on target" is then the same band the mixer itself leaves alone.

**Surplus level is drawn as a *portion* of the bar, not a recolour of all of it.** Once the drawn ratio passes the target plus the green band, only the part of the bar above that point is painted orange; everything below stays green. Recolouring the whole bar - which this used to do - answers the wrong question: the useful reading while mixing is *how much* of the level is surplus, and a bar that flips entirely to orange on crossing the band hides exactly that, making the portion that is correct look identical to the portion that is excessive. The split point is clamped inside the drawn bar, so it can never extend past it. The colour is keyed against **whichever target is currently active** (`AutomixProcessor::active_target_ratio_lu`), so the over-voice state is judged against its own higher target rather than appearing permanently "too loud". This is a GUI-only readability threshold and governs nothing in the DSP.
- **COM (Dialogue) momentary loudness**: fills bottom-up like IS, same accent colour, via `AutomixProcessor::dialogue_momentary_lufs()` (never gained, so no pre/post distinction on this side).
- **Guard-band shading on the COM bar**: the band below `com-gate-lufs` is *darkened* (translucent black, not a light tint) and capped with a dim hairline at the threshold - a shadow reads as "this region is inactive", where a highlight would draw the eye to it, and darkening keeps the bar fill legible through the overlay instead of desaturating it, marking the region in which voice detection is switched off. Drawn on the bar rather than shown as a number because the question being asked is "is my commentator above the line, and is the spill below it?" - which can only be answered against the signal itself. COM only; the Bed side has no guard band.
- **Scale**: a vertical axis (tick marks + numbers) drawn **inside** each metered column, immediately beside its own bar with only `SCALE_GAP` (3px) between them. Ratio doesn't get one, since it shares the loudness bars' scale visually by spanning between them.

  **Every scale sits to the right of its bar.** Mirroring the IS column was tried so that nothing would sit between the IS bar and the Ratio bar, and rejected - the handedness of a scale is not just a matter of which side of the bar it is on, and a mirrored column reads as inconsistent with the others.

  Spacing is instead driven by a single invariant, `BAR_TO_BAR_GAP` (51px): the gap every adjacent pair of *bars* shows, edge to edge. That is the figure the eye judges, and it is not the gap between columns - each column carries its scale on the right, and the Ratio bar is centred in a wider column than it needs, so identical column gaps produce visibly different bar gaps. The three column gaps (`GAP_AFTER_SCALED`, `GAP_BEFORE_RATIO`, `GAP_AFTER_RATIO`) are therefore *derived* from it rather than set by hand, and all three bar gaps come out equal: GR->IS, IS->Ratio and Ratio->COM are each 51px.

  The scales were previously separate columns in the meter row. That put each 20px bar centred in a 62px column, so its ticks began some 21px away and read as belonging to nothing in particular; drawing bar and scale together inside one column is what actually puts them side by side.

  Both kinds of scale step by `SCALE_STEP_DB` (6), a multiple of 3, so loudness and gain-reduction ticks land on the same grid and can be read against each other. Loudness runs bottom-up over -60..0 LUFS; gain reduction runs top-down over 0..`GAIN_REDUCTION_METER_MAX_DB` (36 dB - the ceiling is 48, but reductions that deep are a fault condition rather than something to meter finely, and the shorter range makes normal working levels legible). `vertical_scale`'s `top_down` parameter controls tick direction.

  Numbers sit **exactly on their own tick**. They used to be nudged inward at the very top and bottom to keep them inside the allocated rect, which left the first and last values visibly off their lines - the one place a scale has to be trusted. Half a line of overhang at the extremes is the cheaper error.
- **Voice-activity LEDs**: a small green/gray LED (`voice_activity_led`) under the COM bar reflecting `Meters::voice_active`, and a second one under the IS bar reflecting `Meters::is_voice_active` - 18px across with a soft halo while lit, so it carries from across a gallery rather than needing to be looked for; lit when the respective Silero VAD instance currently detects speech (see `Specs/TechnicalConcept.md` section 6). The COM LED shows `AutomixProcessor::com_voice_gated()` - the flag *after* the guard band, i.e. what actually drives the mix - rather than the raw detector output, which would light while the gate was suppressing it. Each sits directly under the bar it describes rather than in a shared row, so it reads as a property of that signal.
- **Duck depth**: one slider per Bed channel group the format has (4 on 5.1, 6 on 5.1.4 and 7.1.2; on 2.0 the section, and its help entry, are left out entirely), in the area the loop readout used to occupy. These are controls, not meters - see the parameter above.

  They replaced a **loop readout** (`loop_bar`): three small horizontal bars showing what each cascade stage was contributing in dB, against one shared scale and one zero line. That was a debugging view of the cascade's internals - useful while the multi-loop design was being tuned, and nothing to mix with once it was. The per-stage figures are still available where they are actually wanted, in `com-is-assist-offline`'s CSV (`r_slow`/`r_mid`/`r_fast`, see `Specs/TechnicalConcept.md` section 9), and `AutomixProcessor::contributions()` still exposes them.

- **State badge** (`state_badge`): the current `MixState`, drawn as a filled rounded rectangle **directly beneath the meter bank**, spanning its full width (`METER_BANK_WIDTH`, derived from the meter columns and gaps so it stays flush if any of them is retuned) at 42px tall, with the label centred at 18pt. It sits with the meters rather than among the controls because it describes what the metering is showing, and that is where the eye already is while mixing. The width is explicit rather than `available_width()` so it stays aligned with the bars instead of stretching when the window is resized. It is the one element that explains everything the gain is doing, so it is sized to be read at a glance rather than scaled to its text - fed by `Meters::mix_state` (an `AtomicU8` discriminant). Since the mixer's behaviour is defined entirely by which of four states it is in, this is the fastest answer to "why is it doing that right now?", so it gets a shape of its own instead of competing with the surrounding labels. The fill is the state's accent colour at low alpha (reads as a tint, not a block) with a stronger outline to hold the edge against the dark background.

  Labels are operator-facing rather than the internal state names - what the mixer is *doing* reads faster on air than which branch produced it - and the colours are a small vocabulary of their own rather than a strict echo of the meter bank's. (Cyan and orange once matched the IS and COM bars directly; since both bars moved to the shared control accent colour, the badge keeps its own palette and the link is no longer literal.) Over-voice gets a colour found nowhere else rather than reusing orange, because orange is already marking *surplus level* on the ratio meter, and reusing it would make "both are talking" and "COM is louder than it needs to be" look alike when they are unrelated conditions.

  | `MixState` | Badge | Colour |
  |---|---|---|
  | `ReleaseToUnity` | **Idle** | grey |
  | `DuckToTarget` | **IS – Voice Mix** | cyan |
  | `InterviewPassthrough` | **Voice Passthrough** | green, as the VAD LEDs |
  | `DuckToOvervoice` | **Overvoice Mix** | purple |

  Note these are *display* labels only. The offline CSV keeps its stable machine-readable tokens (`release`/`duck-target`/`interview`/`duck-overvoice`), which anything parsing them depends on.

Integrated LUFS (`AutomixProcessor::bed_integrated_lufs`/`dialogue_integrated_lufs` from an earlier iteration of this GUI) was dropped as a deliberate simplification, not a gap - momentary is what the automix control loop and this display both care about; `UI.md`'s "IS LUFS-I"/"Comm LUFS-I" wishlist items are considered out of scope unless a concrete need for them comes up later.

**Window size**: `EguiState::from_size(820, 690)` with `ResizableWindow::min_size(760, 650)` - taller than the meter bank alone needs, to seat the state badge beneath it.

**Painted text still has to be allocated.** The voice lamp draws its "Voice" caption with `painter.text` rather than laying it out as a widget, because the word is wider than the 20px bar the lamp has to stay centred on and laying it out would widen the row and drag the lamp off that bar. Painting, though, consumes no layout height - so the lamp has to reserve the caption's height itself (`LAMP_BLOCK_HEIGHT` = halo overshoot + circle + caption gap + caption line). It originally allocated only the 18px circle, and egui duly laid the state badge out across the word "Voice". The caption gap (5px) also has to clear the gate cross, which overshoots the circle by 2px; at the original 3px the cross touched the text whenever the guard band was closed.

**Both level bars share the controls' accent colour.** `control_accent` returns `Visuals::selection.bg_fill` - the exact colour `ParamSlider` fills with - and the IS and COM bars paint with it rather than carrying a cyan/orange pair of their own, so the meter half and the control half of the window read as one instrument. It is read from the live visuals rather than copied as a literal, so the two cannot drift apart. Note the cost: that colour is dark (contrast 2.4:1 against the `from_gray(22)` meter background, where the former cyan was 14.7:1), so the bars read considerably dimmer than before - a deliberate trade of at-a-glance punch for visual consistency. The two bars are no longer distinguished by colour; their captions and positions do that.

**Leader lines tie the Ratio bar to the two levels it is the distance between** (`ratio_leader_lines`): a thin, faint horizontal line from its bottom edge left to the IS bar, and from its top edge right to the COM bar. They can be horizontal, and land exactly, because the Ratio bar is already drawn on the *same* LUFS scale as the loudness bars rather than on a 0..N ratio scale of its own - it spans from `effective_is_lufs` up by `ratio_lu`, which is the COM level by definition, and its bottom edge therefore coincides with the underside of the red gain-reduction block on the IS bar (both resolve to `y_at(dry_bed - reduction)`). The lines make that already-true geometry visible rather than leaving it to be noticed. They are suppressed when the drawn ratio collapses to nothing (COM at or below the ducked Bed), since there is then no span to point at. Painted from the parent *after* the meter row is laid out, so they sit over the columns they cross and are not clipped by them; kept faint (`from_gray(80)`, 1px) because the left leader crosses the IS column's scale numbers.

This is what forced all four captions through `meter_caption` with its fixed 16px height. The Ratio column previously used a plain `ui.label`, which is a line-height tall rather than 16px and started its bar a couple of pixels below the others - invisible on its own, but enough to put the leaders off the levels they point at. `meter_caption` takes a `center_on_column` flag because the Ratio bar is centred in a column wider than itself while a loudness column's bar sits at the column's left edge with its scale beside it.

**Bypass is aligned to the controls column, not to the window edge** (`meters_to_controls_gutter`). It stays in the title row rather than among the tuning parameters - it is the one control an operator reaches for without looking - on the right-hand side, but *right-aligned to where the sliders below it end* rather than to the window edge, which is where it used to sit and read as adrift. `ui.set_width(...)` is what makes that work: it pins the child's max rect as well as its min, giving the right-to-left layout inside an edge to align against (`set_min_width` alone would leave the layout aligning to the window).

The width it is given is **measured, not computed**. Each `ParamSlider` sizes its value box to whatever text it currently holds - "5 LU" against "-32 LUFS" - so the column's right edge cannot be derived from the width constants, and the title row is drawn before the column that would reveal it. The editor therefore carries the measurement from one frame to the next in an `AtomicF32` (`CONTROLS_COLUMN_WIDTH`, the bar-end width, is only the first frame's fallback). This is exact in every frame but the first; the one-frame lag shows only if a value's digit count changes while dragging.

What is measured is the **grids**, not the column. `control_grid` returns its own right edge and the three are maxed together, because the rules dividing the control groups are `ui.separator()`s, which stretch to the full remaining window width and drag the enclosing column's rect out with them - measuring that instead pushed Bypass clear off the right of the window. Since the value boxes are not all the same width, the edge is whichever grid holds the longest one (today the gate's "-32 LUFS"). Alignment is structural rather than a tuned offset: the title row and the content row are built from the *same sequence of items* (left indent, a `METER_BANK_WIDTH`-wide block, the gutter, then the content), so they accumulate egui's automatic `item_spacing` identically and land at the same x. The gutter helper draws the dividing rule for the content row and reserves the identical width blank for the title row, with `CONTROLS_RULE_WIDTH` pinned rather than left to `Separator`'s default so the two cannot disagree. Zeroing `item_spacing.x` would have been the more direct fix and was rejected: a horizontal `Ui`'s spacing is inherited by its children, and the controls column's own label/slider rows depend on it.

**Meter captions name their input channels.** The IS column carries the format's main-bus channels under its name (`Ch 1-2`, `Ch 1-6` or `Ch 1-10`) and COM carries `Sidechain`, in a smaller, dimmer second line. A host gives no indication of which input the plugin expects what on, so stating it on the meters answers a patching question that otherwise needs the documentation. `meter_caption` reserves `CAPTION_BLOCK_HEIGHT` for **all four** columns including GR and Ratio, which have no channel line: the bars start directly below the caption, and the Ratio bar's leader lines are only exact while every bar shares one top edge.

**About/help overlay** (`help_window`, opened by the `? Help` button beside Bypass - labelled rather than a bare glyph, since a lone `?` is a guess until hovered and this is the control a new operator most needs to find): version, authorship, the channel layout, and a one-line description of every control. An `egui::Window` rather than a panel, so it opens *over* the mixer without the layout underneath shifting - the meters stay where they were while it is being read. Its open state is a GUI-only `AtomicBool` living with the editor, not a parameter, so it never reaches a saved session.

The control descriptions (`PARAMETER_HELP`) are written for someone at the desk rather than someone reading the source - the trade each control makes, not what it is wired to. `Specs/UI.md` is the longer form of the same material.

**Version** (`DISPLAY_VERSION`): a release build is stamped with its GitHub release tag by the release workflow setting `COMIS_RELEASE_VERSION`; anything else reports `dev build (<crate version>)`. Reporting `CARGO_PKG_VERSION` on an unstamped build would claim a release that was never cut, which is the wrong answer precisely when someone is telling you which build is misbehaving. A whitespace-only value counts as unset, so a CI variable that exists but was never filled in cannot produce a blank version.

It is resolved in `build.rs` rather than by an `option_env!` in the source so the rebuild dependency is explicit (`cargo:rerun-if-env-changed`) rather than inferred from rustc's dep-info, and so the fallback lives in one place. A unit test asserts the constant is never empty and matches the tag when one is set. `.github/workflows/release.yml` sets it from `github.ref_name` on a `v*` tag; every other build, including that workflow's `workflow_dispatch` path, passes an empty value and so reports a dev build.

**Layout padding**: the meter bank, the title, and the controls section all share a consistent `CONTENT_LEFT_PADDING` (32px) left indent so nothing sits flush against the window's left edge; the window content also has top and bottom breathing room (`ui.add_space` before the title and after the last control row). Window size (`EguiState::from_size` / `ResizableWindow::min_size`) was increased to 700x560+ minimum to fit the taller bars and the side-by-side meters/controls split.

**Controls** - the column has no heading; the controls are self-labelling and a "Controls" title only cost vertical space. Every row shares a fixed `CONTROL_LABEL_WIDTH` for its name and `CONTROL_SLIDER_WIDTH` for its slider, so rows laid out *outside* the grid (the voice-detect gate, behind its own rule) still line their sliders up with the ones inside it - an auto-sized grid column would leave them half a word out.

`bypass` sits on the title row, right-aligned, deliberately apart from the tuning parameters: it is the one control an operator reaches for without looking. Every other parameter from the "Parameters" section above is exposed in the controls column, still routed through `ParamSetter` (so host automation/undo/preset-recall works identically to the host's own generic parameter UI):
- `target-ratio` ("IS voice ratio"), `overvoice-ratio`, `max-gain-reduction-db`, `attack-ms`, `release-s`, `tolerance-lu` - via `nih_plug_egui::widgets::ParamSlider`, in one aligned two-column grid, with `fast-stage` as a checkbox in the same grid so it lines up with the sliders.
- **Active-target tint** (`ratio_control_row`): the two ratio controls are mutually exclusive targets - only one is in play at a time, decided by the state machine - and which one is not otherwise visible from the controls. The live one has its *name* tinted with a light rounded rectangle in that state's own colour - behind the label only, not the slider, since running it under the control would read as the control being highlighted or disabled rather than as a status (cyan for `DuckToTarget`, purple for `DuckToOvervoice`), so the control and the state badge agree without having to be compared. The tint is painted *behind* the widgets by reserving a shape index and filling it once the row's rect is known, which is the only way to get a background under widgets whose extent egui decides during layout.
- `com-gate-lufs` ("Voice detect gate") sits on its own below that grid, behind a rule: it gates *detection* rather than shaping the mix, so it belongs with neither the tuning parameters above it nor the routing group below.
- `bypass` (title row) and `mix-dialogue-to-bed` - via a plain `ui.checkbox` bound through `ParamSetter::begin_set_parameter`/`set_parameter`/`end_set_parameter`, since `nih_plug_egui` has no built-in bool-parameter widget (`ParamSlider` only handles continuous/stepped ranges).
- **Bus-insert group**: `mix-dialogue-to-bed` and `divergence` sit together below a horizontal rule, separated from the tuning parameters above because they concern *routing* rather than how the automix behaves. `divergence` is placed directly under the toggle it depends on and is wrapped in `ui.add_enabled_ui(mix_dialogue_to_bed, ..)`, so it greys out when the mix is off - it only places Dialogue *within* the Bed, so with the mix off it controls nothing. Greyed rather than hidden, so the relationship between the two stays visible instead of the control appearing and disappearing.

**Title row**: the plugin name is drawn with `RichText::size(23.0).strong()` rather than `ui.heading()`, so it reads as a title slightly above egui's default heading weight and size.

## Building

`nih-plug` doesn't publish to crates.io - it's a git dependency. Bundling uses a workspace `xtask` crate (wrapping `nih_plug_xtask::main()`) plus a `.cargo/config.toml` alias:

```shell
cargo xtask bundle com-is-assist-vst3 --release
```

Produces `target/bundled/Com-IS-Assist.vst3`.
